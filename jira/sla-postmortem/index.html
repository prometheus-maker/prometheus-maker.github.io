SLA Breach Postmortem

A weekly, cause-tagged report of every SLA breach in a service desk.

Scan a service desk each week, tag every SLA breach with an observable cause and post a digest to a tracking issue.

What it does

A missed SLA target is easy to see on one request and hard to explain for a whole week. Was the queue unstaffed, was the request bounced between agents, or did nobody answer while the clock ran?

SLA Breach Postmortem takes one service project and one week - the previous ISO week, Monday 00:00 UTC to Monday 00:00 UTC - reads every request updated in it, and checks each SLA metric. Every breach inside that window becomes a row with the request, the metric and the exact breach time, plus a cause assigned by a fixed rule set, first match wins: unassigned at the breach, reassigned twice or more before it, no reply from an agent account before it, low or lowest priority at it, or unclassified with the status the request held longest.

The scan is paced at 20 requests per run on a five-minute trigger and shows progress on the admin page. Reports are stored per week, kept for the last 26 weeks, and browsable with a filter per cause. When a week finishes, the app posts a digest comment on the tracking issue you nominate: the breach count, a few example breaches, and the totals per cause.

Weekly runs start on their own, and a past week can be rerun for up to 26 weeks back. The project is checked against the SLA endpoint when you save it, so a non-service project is refused. Only Jira administrators open the page or start a run. Reports, the week index and cached display names are deleted on uninstall.

Install

Where to install it: Jira Cloud, from the Atlassian Marketplace.

Open Apps → Manage your apps in Jira, choose Find new apps, search for the app name and click Install.

What you can do with it

You find it under Jira settings → Apps → SLA Breach Postmortem.

  • Weekly scan of one service project's previous ISO week, started automatically
  • Every breached SLA metric read from the request, with the exact breach time
  • Five cause rules: unassigned, reassigned, no agent reply, low priority, unclassified
  • Report per week with counts per metric, cause and assignee
  • Digest comment posted on a tracking issue you nominate
  • Rerun any of the last 26 weeks from the admin page
  • Batched at 20 requests per run; stored data removed on uninstall

Your data

The app runs on Atlassian Forge inside your own site. Settings and any cached results are stored in Forge storage, which belongs to your site; nothing is copied to another service, and nothing is read beyond what the app needs to do its job. Removing the app removes what it stored. Details: privacy policy.
