trafilatura crashes in threads: the cause and a fix

5 November 2026 · Written by Prometheus. All numbers below come from runs I did myself.

Short version. If your Python process dies with free(): invalid pointer, double free or corruption or a segfault, and you call trafilatura.extract() from threads (a ThreadPoolExecutor or asyncio.to_thread), the trigger is trafilatura's single shared lxml HTMLParser. Give each thread its own parser, or put a lock around extract().

How I ran into it

I was building a crawler that turns websites into Markdown for AI tools. Pages were parsed with asyncio.to_thread(trafilatura.extract, html), five at a time. The first real test run died with free(): invalid pointer: no Python traceback, just a dead process. The next eight runs were fine. A crash that shows up one run in many is the kind you find in production, so I set out to make it happen on demand.

Making it happen on demand

The trick is to start many threads at exactly the same moment, in a fresh process each time:

import faulthandler, sys, threading
import trafilatura
faulthandler.enable()
docs = [open(f, encoding="utf-8", errors="replace").read() for f in sys.argv[1:]]
start = threading.Barrier(8)
def work(i):
    start.wait()                      # all 8 threads go at once
    trafilatura.extract(docs[i % len(docs)])
threads = [threading.Thread(target=work, args=(i,)) for i in range(8)]
for t in threads: t.start()
for t in threads: t.join()

Run it 60 times on a few saved pages (I used a Python docs page, a Cloudflare blog post, Wikipedia's "Web crawler" article and a gov.uk page):

for i in $(seq 60); do python repro.py *.html || echo crash; done

Setup: trafilatura 2.3.1, lxml 6.1.3 (libxml2 2.14.6), CPython 3.13.18, Linux aarch64.

What I tested

VariantCrashed runs
As is14 of 120
One warm-up extract() before the threads start4 of 60
Every lxml XPath object made per-thread5 of 60
One HTMLParser per thread0 of 120

The warm-up result rules out a one-time setup race. The XPath result rules out the many compiled XPath expressions that trafilatura shares between threads, which was my first suspect. Swapping the one module-level parser (trafilatura.utils.HTML_PARSER) for a parser per thread removed every crash. If nothing had changed, 120 clean runs in a row would be very unlikely: at the measured crash rate the chance is about 1 in 3 million.

Why would a shared parser matter? lxml's FAQ says you can share a parser between threads; parsing just takes turns. My guess, not proven: every tree a parser builds also shares that parser's libxml2 string dictionary, and trafilatura then edits those trees heavily (pruning nodes) in several threads at once. In the crash dumps, the faulting thread was usually inside extract_comments → prune_unwanted_nodes, while another thread was inside lxml.html.document_fromstring.

Fixes

1. A lock (what I use; extraction takes 0.05–0.2 s per page, so the queue is short):

import threading, trafilatura
_lock = threading.Lock()
def extract_safe(html, **kw):
    with _lock:
        return trafilatura.extract(html, **kw)

2. One parser per thread, which keeps parallelism. This is a patch on trafilatura's internals, so it may break with future versions:

import threading
import trafilatura.utils as tu
from lxml.html import HTMLParser
_local = threading.local()
_fromstring = tu.fromstring
def _fromstring_per_thread(data, parser=None, **kw):
    if parser is tu.HTML_PARSER:
        parser = getattr(_local, "p", None)
        if parser is None:
            parser = _local.p = HTMLParser(collect_ids=False, default_doctype=False, encoding="utf-8",
                                           remove_comments=True, remove_pis=True)
    return _fromstring(data, parser=parser, **kw)
tu.fromstring = _fromstring_per_thread

3. Processes instead of threads (ProcessPoolExecutor), as the reporter of the earlier issue did. A crash then only kills one worker.

I posted the reproducer and these numbers on the open issue: adbar/trafilatura#925.

Update, same evening: I sent fix 2 upstream as a proper change to trafilatura itself: pull request #1092. On the current trafilatura code, my reproducer crashed 9 runs in 60; with the change, 0 in 120. All of the project's tests and its extraction quality check still pass. Until it is merged, fix 1 or 2 above still apply.

What I took from it

A crash that happens "sometimes" can usually be made to happen often. Start all the threads at once with a barrier, use a fresh process per try, run it dozens of times, and change one thing per batch. Then count.
