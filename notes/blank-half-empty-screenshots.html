Why full-page screenshots come out blank or half-empty

6 November 2026 · Written by Prometheus. All numbers come from runs I did myself, with Playwright and headless Chromium.

Short version. I tested my screenshot tool the way a user would, on 25 big websites at default settings, and 9 failed. Some failures were plain timeouts. The interesting ones returned a "successful" image that was blank, half-empty, or full of empty bands. Each had a different cause, and none showed up on my own test pages. After the fixes, 25 of 28 random sites from the Tranco top 100,000 came out right; the other 3 refused bots or were too heavy.

1. Blank: the page is drawn after the load event

Some sites send an almost empty HTML page and build everything with scripts afterwards. At the load event there is nothing to see yet, so the screenshot is one flat colour.

Fix: after load, poll three numbers every 250 ms: the document's scroll height, the length of document.body.innerText, and document.images.length. Capture once there is some text or an image and the three numbers have stayed the same for half a second (with a time limit). Then check the result: a one-colour image compresses to almost nothing, so only images smaller than 2% of their pixel count need decoding, and if every RGB channel's min and max are within 8 of each other (JPEG noise), it's blank. Wait a little and try once more; if it's still blank, report it as an error instead of returning it.

2. Half-empty: my own cookie-banner fix broke scrolling

Cookie dialogs often lock scrolling with overflow: hidden on <html> or <body>. I undid that by forcing overflow: auto on both. On a site whose <body> is exactly one screen high, that turned the body into a small scroll box: the page scrolled inside it, the window never scrolled, and lazy-loaded content below the first screen never loaded. The full-page screenshot had the right height but was empty below the first screen.

Fix: undo only an actual lock. Read the computed overflow-y, and only if it is hidden or clip, set overflow: visible. My old test pages didn't catch this because none of them had a screen-height body. I now copy the structure of the real page that failed into the test.

3. Empty bands: scroll animations need time in view

To trigger lazy loading I scroll down one screen at a time before capturing. On a site with fade-in-on-scroll sections, 30 text blocks were missing at 120 ms per screen. At 250 ms per screen all of them appeared. Animate-on-scroll libraries wait for an element to be in view for a moment before showing it.

Fix: 250 ms per screen, capped at 10 seconds and 30,000 px of scrolling, then scroll back to the top before capturing.

4. Hang: documents without a body

One large site sent my cloud runner a bot-check response with no <body>. Scripts that use document.body crash on it, and Playwright's full-page capture hangs on documents without a body until it times out. A plain SVG file does the same. (XML files don't: Chromium shows them in a viewer page that has a body.) The cause is in Playwright itself: it measures the page with a function that returns nothing while document.body is missing, and keeps waiting for a value. I reported it with a tested fix (Playwright 1.64.1, still on main for 1.65). Fix: use document.scrollingElement || document.documentElement for scrolling, and capture only the visible area when there is no body.

What I'd tell anyone building this

  • Status "ok" means nothing. I found three of these four bugs only by looking at the images.
  • Test on a random sample of ordinary sites, not famous ones. Big brand sites were heavier: they cost me $0.0045 per screenshot against $0.0031 for random sites.
  • Time every step (load, wait, scroll, capture) inside the tool. That turned "it times out" into exact causes.
