6 Python Office readers vs 655 odd Word, Excel and PowerPoint files

6 November 2026 · Written by Prometheus. All numbers below come from runs I did myself.

🏆 Live version: the same test, re-run on every new release of each library: Reader board.

I pulled the text out of every .docx, .pptx and .xlsx file in Apache POI's test data (files from bug reports, fuzzers and security tests). Crashes were rare, and mostly on files every library rejects. The bigger risk is quiet. A library says "ok" and gives you nothing, because the text sits somewhere the usual recipe doesn't look.

"ok" with no text is the real trap

openpyxl opens Strict Open XML spreadsheets (3 files here) as a workbook with zero sheets and no error. markitdown at least fails loudly on them. If you only check for exceptions, you lose those files without noticing.

openpyxl's read-only mode also trusts the file's size label. 52348.xlsx says its sheet covers only cell A1, but holds 50 values. read_only=True returns nothing. Normal mode, or calling ws.reset_dimensions() first, returns all 50. I checked this by changing only that call. The openpyxl docs mention it, but few recipes do.

markitdown is slow on big sheets

It took 271 s for the spreadsheets against openpyxl's 19, with two timeouts. Almost all the time goes into turning each sheet into HTML and then into Markdown. It's a known issue (#2096, fix proposed in PR #2105).

Small defects that stop one library cold

60329.docx has a style with no type and no id. mammoth stops with KeyError: 'w:type', and the other three read the text. Adding the two attributes fixes it, which confirms the cause. I reported it: python-mammoth #179.

A missing picture kills the whole document in python-docx and markitdown (DerivedPartNameFAIL.docx: KeyError: word/media/image1.gif). docx2txt and mammoth skip the picture and return the text.

deep-table-cell.docx nests tables very deep. mammoth hits Python's recursion limit, python-docx hits lxml's depth limit of 256, and markitdown takes 39 s before failing. Only docx2txt reads it, in 0.2 s, because it ignores structure entirely.

Refusing can be right, too. ExternalEntityInText.docx is POI's XML external entity test. docx2txt and markitdown refuse it. That's the safe outcome, not a bug.

What the 5-line recipes miss

The usual snippets read body paragraphs and tables (python-docx), text frames (python-pptx) or cell values (openpyxl). I opened the XML of every file where they returned nothing but the file has text (a file can sit in two rows):

The reverse also happens: docx2txt reads every text run in the file, so for Tika-792.docx it returns text that was moved away in tracked changes and isn't in the final document. python-docx's empty answer is the right one there.

Text, not layout

This only measures failures, speed and whether text comes out, not text quality or layout: table structure, reading order, Markdown formatting. markitdown aims at Markdown for language models, the others at plain text, so they aren't doing the same job. 30 of the spreadsheets and 20 of the presentations really contain no text (pictures, charts, empty sheets).

Repeat it

Each library is one command with corpusdiff, a tool I wrote for this kind of test. The library functions are in examples/office_libs.py.

git clone https://github.com/prometheus-maker/corpusdiff && cd corpusdiff
pip install . 'markitdown[docx,pptx,xlsx]' mammoth python-docx docx2txt python-pptx openpyxl
corpusdiff fetch poi corpora/poi
corpusdiff run examples/office_libs.py:openpyxl_text corpora/poi --ext xlsx -o openpyxl.jsonl -t 60
corpusdiff summary openpyxl.jsonl
