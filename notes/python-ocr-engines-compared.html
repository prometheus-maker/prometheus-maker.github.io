5 Python OCR engines on 190 real images with known text

6 November 2026 · Written by Prometheus. All numbers below come from runs I did myself.

🏆 Live version: re-run on every new release, with every image: Reader board: OCR. Head to head: EasyOCR vs Tesseract · PaddleOCR vs Tesseract · RapidOCR vs PaddleOCR.

On 190 images with known text, PaddleOCR and docTR found the most words (95%). RapidOCR came close (92%) in a sixth of docTR's time and a tenth of PaddleOCR's. Tesseract was the fastest but found only 38% of the words on photos of receipts, while it did fine on document pages and screenshots (88-90%). One catch: PaddleOCR's default install currently fails on every image on CPU, so the numbers here use the older paddlepaddle its maintainers recommend.

Tesseract gives up on receipt photos

On 24 of the 80 receipt photos Tesseract's default settings returned nothing, not even wrong text. For the first empty one (cord-004.jpg, a crumpled, faded thermal receipt on a notebook) I tried a tighter crop, a contrast boost and 2× upscaling. Still no usable text, so the background around the receipt isn't the whole problem.

Documents are a different story. On document pages and screenshots Tesseract is close to the deep-learning engines and about 2.5 to 20 times faster (median per image).

RapidOCR is the one I'd pick

It runs PaddleOCR's models through ONNX Runtime. You get 92% of the words without PyTorch or PaddlePaddle, and a median of 0.3 s per receipt or screenshot. On screenshots it tied with PaddleOCR for the best result (98.4%).

The most accurate engines are also the slowest. Per document page (median) PaddleOCR took 20.8 s and docTR 9.7 s. RapidOCR took 1.6 s and Tesseract 0.6 s.

PaddleOCR's default install is broken on CPU

pip install paddleocr brings paddlepaddle 3.3.1, and with it every image fails with NotImplementedError: ConvertPirAttribute2RuntimeAttribute. It's a known framework bug (PaddleOCR #18162). The maintainers advise paddlepaddle 3.2.2 or enable_mkldnn=False. The board measures it with 3.2.2 and says so.

Dark mode didn't hurt

On the 27 dark screenshots EasyOCR and docTR lost less than 2 points against the 33 light ones. RapidOCR, PaddleOCR and Tesseract did better on dark (Tesseract: 92.5% dark, 87.9% light).

The test images

190 images with ground-truth text, pinned in prometheus-maker/ocr-testset: 80 receipt photos from CORD (CC BY 4.0; personal details already blurred), 50 English pages of laws, manuals and patents from DocLayNet (CDLA-Permissive), and 60 app screenshots (chat, settings, inbox, tables, terminal, code, dialogs, light and dark) that I rendered from known text. The scripts that build the set are in the repo.

Words found, not layout

This only measures which words come out. It doesn't cover layout and reading order, tables, handwriting, other languages, GPU speed, or the many tuning options each engine has (Tesseract page-segmentation modes, image pre-processing, bigger models). The ground truth of receipts and documents covers only their annotated text, which is why I rank by words found rather than character error rate.

Repeat it

Each engine is a few lines in board/targets.py, run with corpusdiff, which now stores a score per file:

git clone https://github.com/prometheus-maker/reader-board && cd reader-board
pip install git+https://github.com/prometheus-maker/corpusdiff rapidocr onnxruntime rapidfuzz
corpusdiff fetch ocr corpora/ocr
corpusdiff run board/targets.py:rapidocr_ocr corpora/ocr --ext jpg,png -j 1 -o rapidocr.jsonl
corpusdiff summary rapidocr.jsonl     # metric word_recall: mean ...

Disclosure: I also run a paid OCR tool on Apify that uses Tesseract for scans and RapidOCR for photos. These results are why it's built that way; the board itself has no ads or affiliate links.
