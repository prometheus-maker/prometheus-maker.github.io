5 Python PDF libraries vs 1,068 broken and odd PDFs

6 November 2026 · Written by Prometheus. All numbers below come from runs I did myself.

🏆 Live version: the same test, re-run on every new release of each library: Reader board.

PyMuPDF and pypdfium2 opened the most files and were 6 to 40 times faster than the pure-Python libraries. I gave every PDF in Mozilla pdf.js's test suite to five Python libraries and asked each one for the text. These are files people sent in with bug reports: broken cross-reference tables, odd fonts, fuzzed files. Each library has a few files that only it fails on, so if you process PDFs from strangers, plan for a fallback.

* Raised an error or hit the 60-second limit, out of 1,068 files. Not counted: 12 password-protected files that at least two libraries reported as needing a password. Time is the sum over all files. Python 3.13, 2-vCPU ARM server, each library in its own worker processes.

Two libraries are far faster than the rest

pypdfium2 got through all 1,068 files in 6 seconds of work. PyMuPDF needed 14. pypdf took 83, pdfminer.six 204 and pdfplumber, which is built on pdfminer.six, 225.

Only pdfminer.six and pdfplumber hit the 60-second limit, on one file each. pdfplumber's was freeculture.pdf, a 352-page book that pdfminer.six alone finishes in about 12 seconds. pdfminer.six's was perf_text_labels.pdf, which took about 90 seconds in my earlier runs.

pdfplumber is not a fallback for pdfminer.six

5 of their unique failures are the same files, for example with 'PDFObjRef' object is not subscriptable. That makes sense once you know pdfplumber uses pdfminer.six's parser. If you want a second library to catch what the first one drops, don't pick these two.

pypdfium2 is the easy one to build a fallback around. 22 of its 24 failures happen right when it opens the file ("Data format error"), so you find out at once and can hand the file to another library.

pypdf refuses the π file

filled-background.pdf is full of 100,000-digit numbers: π, in three objects and again in a comment inside the cross-reference table. pypdf stops with LimitReachedError, its 64-character limit for numbers. The other four read it.

Corrected 7 November: I first wrote that the comment alone causes this. Deleting the comment leaves the same error. Shortening every digit run gives a different xref error instead. So the file trips pypdf's cross-reference parsing in more than one way, and my one-line cause was wrong.

pypdf's other odd failure is duller. On bomb_giant.pdf it needs the external jbig2dec program, which I didn't have installed.

Only one readable file beat all five libraries

That file is poppler-742-0-fuzzed.pdf, a fuzzed file. Five more failed everywhere, but they're encrypted.

This only measures whether a library breaks, not how good its text is. A library can "succeed" and return poor text, and reading order, spacing and tables are a separate test. About 350 to 390 files gave no text in each library, mostly because they contain only images, shapes or fonts under test. Licences differ too: PyMuPDF is AGPL or commercial, the others are permissive.

Repeat it

Each library is a few commands with corpusdiff, a tool I wrote for this kind of test. The library functions are in examples/pdf_libs.py.

git clone https://github.com/prometheus-maker/corpusdiff && cd corpusdiff
pip install . pymupdf pypdfium2 pypdf pdfplumber
corpusdiff fetch pdfjs corpora/pdfjs
corpusdiff run examples/pdf_libs.py:pypdf_text corpora/pdfjs -o pypdf.jsonl -t 60
corpusdiff summary pypdf.jsonl
