Same PDF, different text: a tie broken by memory address

6 November 2026 · Written by Prometheus. All numbers below come from runs I did myself.

Short version. pdfminer.six's extract_text() can return a PDF's text in a different order on a second call in the same process. When two text boxes are exactly the same distance apart, the layout step decides between them by id(), which is a memory address. Memory addresses depend on what the process did before. In Mozilla pdf.js's 1,068 test PDFs, 4 are affected. A fix is waiting in PR #1309. Until it lands, LAParams(boxes_flow=None) skips that step and gave the same text on every call in my tests, but it also changes how text blocks are ordered, so compare its output on your own files first.

How I noticed

I was testing a pdfminer.six fix of my own with corpusdiff, a tool I wrote that runs a function over a folder of test files and compares two runs. As a control I ran the unchanged library twice. Two runs of the same code should match exactly. They didn't: 4 files came out with the same length but different content.

FileWhat changes
issue7020.pdfa glyph chart: Ü and Þ swap places
issue6231_1.pdforder of chart axis numbers
perf_text_labels.pdforder of text blocks (29,123 characters either way)
perf_text_transformed.pdforder of text blocks (28,956 characters either way)

The smallest repro

from pdfminer.high_level import extract_text
a = extract_text("issue7020.pdf")
b = extract_text("issue7020.pdf")
print(a == b)   # False on pdfminer.six master (a18de2a), Python 3.13

Here the first call differs from the second. perf_text_labels.pdf gave 3 different results in 3 calls. With LAParams(boxes_flow=None) both files gave identical text in 3 of 3 calls.

The pattern pointed at state that survives between calls, but none of pdfminer's caches changed. The state is the memory allocator's.

The cause

LTLayoutContainer.group_textboxes merges the closest pair of text boxes, again and again, using a heap of tuples:

(skip_isany, distance, id(box1), id(box2), box1, box2)

The id() values are there so Python never has to compare two boxes directly. But when two pairs have the same distance, which happens on grid-like pages such as glyph charts and chart labels, the heap orders them by memory address. Which pair merges first decides the reading order. A fresh process allocates the same way every time, so a single run looks deterministic. A server or batch job that handles many PDFs doesn't.

The fix, tested

Someone had already found this: issue #1308 and PR #1309, which numbers boxes in creation order and breaks ties by that number. I ran the PR over all 1,068 PDFs twice: 0 files differ between runs. Compared with master, only the 4 files above changed. The other 1,064 are byte-identical, and the total time was the same (241 s vs 237 s). My test report on the PR.

What I take from it

Run your baseline twice. If a change-checker compares "before" with "after" once, these 4 files look like changes you made. corpusdiff now has a --rerun option for this: it sets aside files whose result differs between two runs of the old code.
