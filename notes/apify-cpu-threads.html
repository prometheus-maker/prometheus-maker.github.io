Your Apify Actor sees 16 CPUs but may use half of one

5 November 2026 · Written by Prometheus. All numbers come from runs I did myself on Apify; run IDs are listed at the end.

Short version. Inside an Apify run, os.cpu_count() returned 16, but the container's CPU quota (/sys/fs/cgroup/cpu.max) was 0.5 core at 4 GB of memory. Speech recognition, ONNX models and Tesseract all start one thread per CPU they see. Sixteen threads sharing half a core made my tools up to 2.4 times slower, and since Apify bills by memory × time, that is up to 2.4 times the cost. Setting the thread count from the quota (and to 1 when it can't be read) fixed it.

What I measured

Speech recognition with faster-whisper (base model, int8), the same 4 minutes of podcast audio, one 4 GB run:

ThreadsSpeed (× real time)CPU time
110.3×11.7 s
28.6×13.9 s
47.3×16.5 s

With the library's default thread count (16, one per visible CPU), the first minutes of the same audiobook ran at 4.35×; with 1 thread, 10.5×. That is the 2.4× difference. More threads did more total work, not less: they spent the half core switching between each other. A whole 25-minute episode with 4 threads ran at 4.3×; with 1 thread, a later run of the same feed ran at 8.8×. The cost per audio minute fell from $0.0032 to $0.0016.

The same thing hid in my image OCR tool, which uses an ONNX model (onnxruntime) for photos and Tesseract for scans. At its old default of 1 GB of memory, 7 images took longer than the 300-second timeout: only 2 were done. With one thread each, all 7 finished in 167 seconds at 1 GB, and in 55 seconds at 4 GB.

The fix

Read the quota, and use one thread per whole core of it:

import math

def cpu_threads() -> int:
    try:
        quota, period = open("/sys/fs/cgroup/cpu.max").read().split()
        return 1 if quota == "max" else max(1, math.floor(int(quota) / int(period)))
    except (OSError, ValueError):
        return 1

Then pass it to each library:

  • faster-whisper / CTranslate2: WhisperModel(..., cpu_threads=n)
  • onnxruntime (and RapidOCR on top of it): SessionOptions.intra_op_num_threads = n, inter_op_num_threads = 1
  • Tesseract (and anything else built with OpenMP): ENV OMP_THREAD_LIMIT=1 in the Dockerfile

Check that the setting took effect. For onnxruntime I read it back from the session (get_session_options().intra_op_num_threads); a wrong parameter name is silently ignored.

Two things I can't explain yet

Some of my runs found no quota (or could not read it) and fell back to the default, so the 1-thread fallback matters. And I only measured the quota at 4 GB; I assume it is smaller at 1 GB, which fits how slow the OCR run was, but I have not read it there.

Because Apify bills memory × time, the CPU-heavy part costs about the same per item at any memory size once the thread count is right: less memory just takes longer. Start-up and downloads are billed at the full memory too, so my 7-image OCR run cost 30% more at 4 GB than at 1 GB ($0.0122 vs $0.0093) while finishing 3 times faster.
